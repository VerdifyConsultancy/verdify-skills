## PRODUCT-001 Purpose And Outcome

- Product purpose: Verdify Skills is the internal-first shared agent and method layer that binds planning, contracts, lifecycle execution, review, evidence, release verification, and platform adapters into one self-building software-and-knowledge platform.
- Primary declared customer: the integrated four-project pilot. Verdify Skills, Agent Platform, Orbit, and Gravity are co-equal active projects with their own product intent, authoritative issue backlog, deployment, and outcome acceptance. The root planning agent is the portfolio outer loop that reconciles priorities and dependencies; it does not replace each project's authority.
- Current state: at inspected `dev` head `d226b7f244fd4612ab44739fd275b8158e1d9159`, the repository validates 28 skills and declares package version `1.3.0`. GitHub Actions, GitHub-hosted runners, npm, GitHub Releases, GitHub source/review/status authority, and several public inputs remain load-bearing; the July 9 review also identified package and transition trust gaps. Agents, Orbit, and Gravity remain active but are not yet operating as one trusted loop.
- Target state: one issue can move through evidence intake, North Star planning, project-owned backlog, capability-negotiated dispatch, bounded implementation, fresh criticism, local CI/CD, deployed verification, Gravity evidence retrieval, Orbit context/reporting, and outcome acceptance with every state reconstructable from the configured internal authority and durable artifacts. GitHub may receive a mirror, but its outage cannot stop the path. The four projects can then use the same platform to build the next increment of the platform itself and onboard customer consulting projects through the same governed method.
- Proposed iteration-26 distribution, subject to `NSQ-017` and legal/IP confirmation: Verdify Skills is primarily an internal capability whose repository is already public and whose package declares `UNLICENSED`. The public surface would be proprietary/source-available: GitHub's Terms supply in-Service view/use/display/perform/reproduce/fork rights, while the project would make no separate grant beyond those Terms and applicable law for off-platform use, modification, redistribution, derivative works, or package use. Parties may have separate written terms. External community growth and a public compatibility promise are not current product goals.
- Compatibility: no backward-compatibility obligation is assumed. Deprecated or redundant capabilities should be removed after an atomic consumer convergence rather than carried as indefinite aliases or shims.
- Non-goals: do not build an external community, preserve deprecated behavior for its own sake, grant broad production mutation rights, perform a flag-day migration, treat warm caches as offline proof, or infer a future North Star lock from ordinary review or release activity.
- Success measures: all four pilots expose current lifecycle, capability, gate, runtime, evidence, and outcome state; one integrated vertical slice closes end to end; trusted package and transition gates are enforced; the system can select and complete its next bounded improvement without private chat state; a customer consulting repository can be onboarded without inventing a second lifecycle.
- Evidence: all registered evidence items, especially the July 9 adversarial review, Jason feedback, explicit iteration-25 lock approval, and fresh Agent Platform, Orbit, and Gravity audits (`northstar://evidence/NSE-20260709-*`), supported by the earlier delivery, security, GitOps, observability, session-ledger, control-request, backlog-sync, and learning-loop research.

## PRODUCT-003 PRD Summary

- Problem: the four active projects have useful but drifting lifecycle, runtime, information, and evidence capabilities. Without one outer planning loop, shared contracts, safe package distribution, and versioned integration interfaces, each project can advance while the platform as a whole remains unable to build itself reliably.
- Users: Jason, James, the root planning agent, pilot project owners, Orbit, worktree agents, reviewers, controller agents, platform operators, and Gravity evidence consumers.
- Jobs to be done: ingest evidence, maintain four project North Stars and backlogs, negotiate platform capabilities, execute bounded lanes, prove runtime deployment, retrieve cited Gravity evidence, turn authorized personal and enterprise context into Orbit workflows, and continuously select the next highest-value platform improvement.
- Minimum useful scope: research ingest, transcript replan, North Star artifact loop, repo hygiene, controller-loop specification, platform readiness, Gravity readiness, state-of-union, sprint planning, lane execution, critic review, and release verification.
- Differentiators: explicit North Star governance, a root-planner portfolio loop, common pilot and capability contracts, thin optional conversational adapters, repo-controller bootstrap/self-discovery, CI/CD wave lifecycle, review inbox, session ledger, proposal-only learning capture, loop-readiness checks, fleet observability and recovery, governed Orbit information workflows, current Gravity evidence interfaces, trusted package transactions, and traceable human-governed autonomous delivery.
- Out of scope: uncontrolled production autonomy, indefinite deprecated compatibility, a public community program, and treating an optional OpenClaw or Hermes implementation as the source of platform authority.
- Dependencies: the configured internal Git/review/status authority, repo-local instructions, `.agent-workflow` artifacts, Argo Events and Workflows, Zot, GitOps reconciliation, internal immutable dependency mirrors, observability, and credential/RBAC boundaries. GitHub, npm, and public release surfaces are coexistence mirrors rather than target-state prerequisites.
- Planning loop: distill evidence, propose research, answer questions where evidence supports an answer, propose design, accept human feedback, return to the loop, and request final lock approval only when the North Star is ready to advance to the next milestone.
- Owned-IP bias: own the root-planning method, lifecycle/evidence contracts, capability adapters, Orbit information workflows, and Gravity evidence interfaces while composing commodity Git, Kubernetes, GitOps, identity, database, connector, vector, and observability primitives.
- Evidence: all registered evidence items.

## PRODUCT-015 Local Delivery Independence

This section is the proposed iteration-26 delta. It supersedes the
GitHub-as-permanent-authority and npm-as-primary-publication assumptions only
after Jason records final lock and the attended cutover completes. Until then,
iteration 25, `COMMON_OPERATING_CONTRACT.md`, `config/authority-matrix.yaml`,
GitHub protections, and existing release behavior remain authoritative.

### Outcome and boundary

- A capability-qualified supported Forgejo release is proposed as the internal
  authority for repositories, issues, pull requests, reviews, required
  statuses, protected branches, audit, and portfolio work. Version 16 is the
  current review candidate, not a permanent version pin; the deployed release
  must pass the authority contract and have an upgrade policy.
- Git push mirroring is not governance migration. Provider-neutral repository,
  work-item, change, review, status, and evidence IDs map imported history,
  portfolio metadata, and cross-system references. Imported approvals remain
  historical and cannot satisfy a new protected merge.
- Shared Agent Platform issue `jvallery/agents#3047` owns the reusable internal
  Git/event/status authority and offline dependency supply. Repository issue
  `#3044` owns Verdify Skills adoption, parity, package, and consumer evidence.
  Both remain proposals until their respective approvals and contracts exist.
- GitHub source, Releases, and npm become output mirrors with a public support
  contract. They do not become implicit failback authorities. Recovery restores
  the internal authority as one coordinated control plane; any emergency
  authority transfer is a separate human-gated decision.
- An internal IdP supplies immutable human subjects, MFA, deprovisioning, and
  break-glass records. Candidate, validator, critic, status, publisher, signer,
  mirror, GitOps, verifier, approver, and recovery principals are distinct.
- A dedicated event-admission service verifies the raw Forgejo webhook body and
  signature before emitting a normalized event. A durable transaction/effect
  ledger owns deduplication, compare-and-set state, payload hashes, exact-head
  currentness, side-effect receipts, immutable archives, and authorized replay.
  Argo Events and a replicated persistent EventBus transport admitted events;
  Argo Workflows execute repository-owned policy but are not the transaction
  authority.
- The released product is an immutable Verdify package subject in Zot plus one
  signed immutable release envelope enumerating the complete pre-promotion
  source, protected policy, exact package, checksums, tests, provenance, SBOM,
  signing, attestations, and criticism graph. The durable ledger advances that
  fixed digest through staged, verified, approved-for-nonproduction,
  consumer-verified, released, mirrored, rolled-back, and retired states and
  records later approval, GitOps, consumer, rollback, and mirror effects.
- The non-production acceptance environment is a stable digest-pinned harness
  Deployment. Its init container pulls and verifies the package and release
  envelope into a fresh volume; its main container performs a real install and
  representative lifecycle probes before readiness. Argo CD is the sole
  desired-state mutator, using an internal desired-state repository and explicit
  namespace, kind, and field-manager allowlists.
- No direct production mutation, workflow disablement, branch-protection
  change, credential removal, runner removal, public-package deletion, release
  deletion, or GitHub disconnection is authorized by this draft.
