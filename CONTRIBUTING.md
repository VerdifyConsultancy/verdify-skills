# Contributing

Changes should begin with a GitHub issue that states the problem and desired outcome. Implementation pull requests target `dev` and must link that issue with a supported closing keyword; discovered maintenance work belongs in the backlog rather than an undocumented exception.

`dev` is the long-running development integration branch. `main` is the protected release branch and should only be updated by the generated `dev -> main` release PR. Every push to `dev` opens or updates that release PR; merging it to `main` triggers the npm publish workflow.

Before opening a pull request:

```bash
make links
make test
```

Use `.github/pull_request_template.md` exactly: keep the required section headings, close the backing issue with a supported keyword, include the lane contract path, record the last substantive `Implementation head SHA`, record the closeout-only `Evidence head SHA`, and set `Current head SHA` to the exact 40-character PR head commit. The critic report must be the only change after the evidence head, and a repository admin or maintainer other than the PR author must submit an `APPROVED`, commit-bound review on the resulting current head. Policy CI executes the validator from the protected base checkout and treats the full candidate checkout only as input. Skill changes must keep `SKILL.md` below 500 lines, use progressive disclosure, preserve one canonical schema location, add or update evaluation scenarios, and commit the `.agents/skills/<skill>` plus `.claude/skills/<skill>` symlinks generated by `make links`. Workflow changes must update `verdify.workflow.yaml`, relevant documentation, and examples.

A centrally-rendered agent-fleet CI/CD contract refresh from `jvallery/agents` (the managed sentinel span in `AGENTS.md`/`CLAUDE.md` plus the generated `.agent-fleet/ci.yaml`) uses `.github/PULL_REQUEST_TEMPLATE/fleet-contract-sync.md` and the `verdify:fleet-contract-sync` label instead of the full lane contract. The label alone does not exempt anything: both `pull-request-policy` and `critic-gate` additionally require `Verdify::ManagedContractDiff` to mechanically prove the diff touches only that managed surface plus `MANIFEST.sha256` — a PR that carries the label but changes anything else is rejected outright, not silently downgraded to a weaker check. This exists only for refreshes to an *already-adopted* contract; a repo's first-time adoption still goes through the full lane contract (see #239 for this repo's own precedent).

Do not add a dependency without explaining why Ruby, Git, Bash, and GitHub CLI are insufficient.
